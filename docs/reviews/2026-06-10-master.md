# Code Review — av-opencode-plugins (master, pełne repo)

**Data:** 2026-06-10
**Zakres:** całe repozytorium (root `src/`, `scripts/`, `packages/*`), nacisk na kierunek migracji plugins → harness AI (Pantheon)
**Metoda:** security-auditor + code-quality-auditor + documentation-auditor (równolegle), analiza wydajności i architektury koordynatora, weryfikacja Cross-Verifier + Challenger

## Werdykt: kierunek migracji do harnessu AI

**Kierunek jest dobry, a kluczowa granica architektoniczna jest realnie wymuszona, nie tylko zadeklarowana.**

- **Granica src→packages: PASS.** Grep każdego `.ts` pod `packages/*/src` nie znalazł żadnego importu z root `src/`. Odwrotny kierunek poprawny: `src/index.ts` importuje wyłącznie `packages/*/dist/index.js`.
- **Warstwy wewnątrz `src/`: prawie czyste.** Featury zależą od `_shared/` i bibliotek (`agent-registry`, `agent-roster`, `pantheon-config`); cross-feature wiring idzie przez `_shared/dispatch-extensions.ts`. Jedna inwersja (ARCH-001) — jedyna rzecz w `src/` aktywnie walcząca z kierunkiem migracji.
- **Bezpieczeństwo: wyjątkowo dojrzałe.** Sandbox przepisów QA przetrwał fuzzing 13 payloadami obejść, sanitizer anty-injection działa na 8 ujściach, ścieżki skills mają allowlist exact-match, supply chain czysty (344 zależności wyłącznie z rejestru npm, override `uuid` działa). Ocena audytora bezpieczeństwa: "unusually well-hardened".
- Root `tsc --noEmit` przechodzi czysto; 106 plików testowych; inwarianty synchronizacyjne (PERUN_TOOLS ↔ perun.md itd.) pilnowane testami.

Realny dług to nie kierunek, tylko **skalowanie procesu absorpcji**: ręczna enumeracja workspace'ów w 4 miejscach, duplikacja builderów promptów rosnąca liniowo z każdym wchłoniętym agentem i jeden niewymuszony inwariant kolejności.

## Znaleziska (po weryfikacji adwersaryjnej)

### [MEDIUM] ARCH-001: Sanitizer bezpieczeństwa w module feature — inwersja warstw `pantheon-config → coordinator`
**Status:** ✅ Fixed (2026-06-11)

**ID:** ARCH-001
**Lokalizacja:** `src/modules/pantheon-config/loader.ts:4`, `src/modules/pantheon-config/schema.ts:9`
**Kategoria:** Architecture
**CWE:** CWE-117 (kontekst)
**Effort:** medium
**Status:** [verified] (Challenger: HIGH→LOW/MEDIUM; podniesione do MEDIUM przez COMPOSITE-1 Cross-Verifiera — dotyczy prymitywu bezpieczeństwa)

**Problem:** Biblioteka `pantheon-config` importuje `neutralizeUntrustedOutput` "w górę" z `../coordinator/sanitize.js`, a `coordinator` importuje `pantheon-config` — cykl na poziomie nazw (bez cyklu runtime: `sanitize.ts` to czysty liść importujący tylko `node:path`). Jedyne naruszenie kierunku zależności w `src/`.

**Impact:** `neutralizeUntrustedOutput` to jedyny repo-wide neutralizator prompt-injection (OSC/C1/BiDi/zero-width). Gdy `pantheon-config` lub `coordinator` będą pakietowane dalej w migracji, sanitizer trzeba będzie przenieść albo skopiować — niekompletna kopia reguł strip po cichu otwiera z powrotem klasę ataków, którą kod deklaruje jako zamkniętą.

**Remediacja:**

```ts
// przed (pantheon-config/loader.ts)
import { neutralizeUntrustedOutput } from "../coordinator/sanitize.js"
// po — przenieś sanitize.ts do _shared/, re-export w coordinator/ dla zgodności
import { neutralizeUntrustedOutput } from "../_shared/sanitize.js"
```

Potraktuj przeniesienie jako zmianę bezpieczeństwa (test single-source na zestaw reguł strip), nie jako zwykły refactor.

### Skorygowane przez Challengera

- **vitest (A):** CRITICAL→LOW — devDep, wymaga `--ui` + ekspozycji sieciowej + Windows; patch w 3.2.5 (nie 3.2.6).

- Bidi-warningi Semgrepa na `sanitize.ts:62`/`env-config.ts:10` — false positives (literalne znaki bidi w defensywnych regexach).

### Zweryfikowane jako czyste (mocne strony)
