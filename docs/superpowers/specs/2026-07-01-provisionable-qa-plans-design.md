# Provisionable QA Plans — Design Spec

**Date:** 2026-07-01
**Status:** Approved for planning (4 design decisions locked 2026-07-01 — see [Decisions](#decisions-locked)).
**Scope:** Redesign Pantheon's **plan-authoring philosophy** so Veles produces *provisionable* QA plans — plans the runner can actually execute with far less human engagement — grounded in OMO (`oh-my-openagent`) prior art. **Doc-only** (agent prompts + skill markdown); **no `qa-loop` TypeScript changes**. Every security invariant is preserved; everything stays inside the runner's `curl`/`psql`/`Playwright` surface.
**Origin:** A real session transcript (SynergyCodes `workflow-engine`, AI-confidence-score feature) where a Pantheon QA run stalled on un-gettable prerequisites. Companion to the already-shipped in-session fix of the `qa_loop_start` H3/H2 heading parser + empty-dispatch loud-failure (separate change, not part of this spec).

---

## 1. Problem / Motivation

A QA run over the `feature/user-task-ai-confidence-score` branch stalled in a cascade. Four distinct frictions:

1. **Empty `dispatch_set`** — the plan used documented `### BE-01:` (H3) headings but the parser matched only `## BE-01` (H2). **Already fixed this session** (parser now lenient `#{2,4}` + loud error on zero-parse). *Out of scope here; listed for completeness.*
2. **Preflight wall + credential dance** — ~10 env vars missing; the user asked Perun to read `.env` (correctly refused); the preflight prompt still claims credential-prefixed names cannot be chat-pasted, though commit `23ab6bc` made plan-declared Required env vars pasteable. **Stale prompt.** (Verified: `DB_`/`ENTRA_` were never even on the denylist — see §6.)
3. **Guessed auth endpoint** — the `QA_BIND_JWT` recipe hard-coded `login.microsoftonline.com`, but the app's real authority is a **CIAM** tenant (`…​.ciamlogin.com`). The token would fail even with every secret present. Veles **guessed** the endpoint instead of reading the auth config.
4. **Un-provisionable fixture, no fallback** — BE-03/BE-04 required an `AI_WORKFLOW_ID`: a pre-published Temporal+Azure workflow whose agent emits `confidence.score`. The harness cannot create it, and the plan offered no fallback — a hard stall. Meanwhile BE-01/BE-02 *organically discovered the right pattern*: seed a `user_tasks` row via `psql` and test the read path.

### Root cause

Veles jumps from **"read the diff"** straight to **"write live scenarios"**, with no step that asks: *what kind of change is this, and what is the cheapest seam that PROVES it?* That single missing step produced every failure above — it authored heavy live E2E needing an un-provisionable fixture (#4), guessed an endpoint instead of grounding it (#3), and never recorded that the **actual change under test** (the `confidence.score` *propagation* executor→runner→activity→DB) is already covered by a hermetic unit test (`test_extract_confidence_score`) while the live loop only exercises the read-back.

## 2. OMO prior art — what we borrow, what we defer

OMO ships two QA skills (`.agents/skills/opencode-qa`, `.agents/skills/codex-qa`). Its doctrine, and how each piece maps to Pantheon:

| OMO principle | OMO mechanic (pointer) | Pantheon disposition |
|---|---|---|
| **Isolation-first + local mock** | isolated `CODEX_HOME` + local mock model provider so "no real API call" (`codex-qa/references/isolation.md:29-48`) | **Defer to a future harness change** — the runner cannot stand up mocks. Transfers now only as a *plan precondition*: assume a dedicated non-prod target + throwaway DB. |
| **Match QA to change scope (the ladder)** | unit-probe first, live-wiring only to prove wiring, UI last (`codex-qa/references/components-hooks.md:8-14`) | **Adopt now** as the spine — new Step 4.7 provability ladder. |
| **Ground, don't guess** | "verify flags against the installed `--help`"; confirm against the running artifact (`codex-qa/references/app-server.md:8-9,21-25`) | **Adopt now** — auth-authority grounding sub-rule in Step 4.6 (kills the CIAM class). |
| **Evidence-first** | "the captured JSON/pane IS the evidence; no evidence == QA did not happen" | **Adopt now** — the hermetic pointer is the named evidence for the un-provisionable case. |

**Core tension:** OMO's runner *provisions* (docker / mock / isolated home); Pantheon's runner **cannot** — it tests an already-running instance over `curl`/`psql`/`sqlite3`/`Playwright` only (`qa-plan-authoring` Step 4.5). So OMO's doctrine transfers to **plan-authoring now**; its mock/isolation *power* is a separate, later **harness** workstream (see §8).

## 3. Design — five core moves

All five live in `src/skills/qa/qa-plan-authoring/SKILL.md` and `src/skills/qa/test-plan-format/SKILL.md`, plus one **required** companion in `src/modules/plan/veles.md`.

### Move 1 — The provability ladder (new Step 4.7)

Insert a new **`## Step 4.7: Classify the change & pick the cheapest proving seam`** *after* Step 4.6 (test-env detection, line 175) — so tool detection (Step 4) and test-infra detection (Step 4.6) have already run and their outputs (available seams, hermetic test infra) are known when the ladder classifies. For each changed surface, Veles **first runs the provisionability litmus (Move 2)**; only if the trigger is provisionable does it then select the **cheapest live rung** (R1→R3) that still proves *this* change. R0 is not a rung — it is the escape taken **only when no live rung is executable**:

- **R0 — orthogonal escape** for ANY changed surface (logic, data, API, or UI) whose only live trigger is **un-provisionable by the runner** (see the litmus in Move 2), regardless of seam level. Emit **no** live scenario for that surface; record it as a `provisioning-blocked` matrix row (Move 2) carrying that row's mandatory evidence — a `hermetic: <path>::<test>` pointer when a repo test asserts the logic (the preferred evidence for pure-logic / transform changes: a parser/mapper/scorer, the `executor→runner→activity→DB` propagation), **or** a `**Setup prerequisite:**` naming the human provisioning action when no hermetic test exists (e.g. an un-provisionable UI surface), ideally both.
- **R1 — data-layer / read-back**: a `psql`/`sqlite3` seam-seed (INSERT the row) + a read scenario. **The INSERT MUST be schema-grounded** — its columns, every NOT-NULL/FK/CHECK target, and any enum/status literal read from the migration or ORM model in the tree (or, when the schema is not on disk, a **committed** OpenAPI/schema artifact in the tree) and cited `(file:line)`, never guessed. The author has `Read`/`Grep`/`Glob` only and **MUST NOT** run a live `psql`/`curl` schema probe at authoring time. **If no committed schema source exists, `provisioning-blocked` is INVALID** — the row is still psql-mintable, and the Move-2 litmus + §4a hard-stop key on *harness*-mintability, not the author's ability to ground the INSERT (a no-schema `provisioning-blocked` row would itself be hard-stopped and reclassified). Fall back **inside the `covered` channel**: (a) if the tree still yields a plausible column set (the read path's own queries/serializers/DTOs), author the seed with every unconfirmed column/enum/status literal tagged `(unverified — confirm at run time)` and a `**Coverage delta:**` naming the unconfirmed INSERT shape as the unproven link; (b) if not even a plausible column set is inferable, drop the seed and author only the live read scenario tagged `(unverified — confirm at run time)`, whose **first assertion is an existence check** on the manually-seeded precondition row — failing loudly as *seed-missing*, not as a code defect (the same guard the split-seed rule mandates; be-testing's `(unverified)` handling only downgrades a mismatch to LOW, so without this check the misattribution survives) — with a `**Coverage delta:**` stating the row must be seeded manually because the schema is not in the tree. `provisioning-blocked` stays reserved for artifacts the four tools cannot mint at all. The seam-seed INSERT is a **scenario step the BE runner executes as a single raw `psql`/`sqlite3` statement** (`Bash(psql:*)`/`Bash(sqlite3:*)`, `allowed-tools.ts:46-47`) — **not** via `execute_recipe` (that sandbox is provisioning-only, `zmora-setup`-only, `perun.md:35-36`; Stribog's between-waves fixture path `perun.md 3.8` only mutates an *already-identified* row, not a from-scratch seed). Because the author cannot probe live, a guessed column/enum/FK target fails at run time and silently voids the read scenario it feeds — an ungrounded seam-seed is a coverage defect, not R1 coverage. **The seed executes ONLY against the plan's declared DB.** A `**Seed (psql/sqlite3):**` step carries the fenced SQL **plus exactly one connection reference** — the `$VAR` env-var name (or literal DSN) declared under `## Setup` `**Required databases:**`/Required env vars — e.g. the executor composes `psql "$DATABASE_URL" -c '<fenced SQL>'`; it MUST NOT reference any other target. The connection reference must live **in the scenario block**, because the dispatched zmora-be child receives only the sanitised scenario block + Base URL (perun.md dispatch shape) — never `## Setup` — and overlay-be's existing machinery (Step 2.5 in-child `$VAR` env preflight; Step 3 item 4's DB auth-failure `NEED_INFO`) keys on in-scenario tokens. Unlike the recipe sandbox (`recipe-validator.ts:448-466`), the scenario path has **no machine-enforced DSN egress check** — and for the `$VAR` form the host is injected only into the zmora child at runtime (`shell-env-hook.ts`), **unresolvable at Perun's pre-dispatch sanitize time**, so `perun.md:133` provides no host-level bound for the seed. The operative egress guards are the plan-declared-token rule + the §7 throwaway-target consent; the amended sanitizer (§4b fourth edit) contributes only declared-token *textual* matching (a plan-time contract, same class as Move 4's paste-time contract). **Author the seed and its read-back as a single scenario** (the INSERT as a first step, then the read assertion + DB Check). A **split** seed/read pair loses BOTH single-scenario guarantees and carries an explicit warning: the mutation guard strips **per-scenario** and is blind to `**Depends-on:**` (a stripped seed leaves the read dispatched when any other scenario keeps the set non-empty), and `**Depends-on:**` guarantees **order only** — predecessor failure does NOT block dependents (`test-plan-format:329`, `perun.md:529`) — so a read whose seed was stripped or failed executes against an empty table and reports a false result, misattributing a seed defect to the code under test. If a split is unavoidable: carry `**Depends-on:** <seed ID>` (Step 6.9) AND make the read's first assertion an existence check on the seeded row that fails loudly as *seed-missing*, not as a code defect.
- **R2 — API / contract**: a `curl` scenario.
- **R3 — UI / wiring / user-visible**: a Playwright scenario.

R1→R2→R3 is the seam-level climb (data→API→UI); **R0 is a gate on the provisionability axis, not the cheapest rung** — picking R0 (no live scenario) when a live R1–R3 rung *can* prove the change is a coverage-honesty defect the Step 6.8 refute must catch. A single change can decompose into surfaces at different rungs — e.g. the AI-score change yields an **R1** read-back scenario *and* an **R0/`provisioning-blocked`** propagation row.

**Rule (stated explicitly in the step):** *"Run the provisionability litmus first. If the trigger is provisionable, pick the cheapest live rung (R1→R3) that proves THIS change and climb only when the change scope crosses the corresponding seam (data→wire→UI) — do not default every change to a browser flow. Take R0/`provisioning-blocked` ONLY when no live rung is executable; choosing it over an available live rung is a coverage-honesty defect."* Cross-reference OMO `components-hooks.md:8-14`.

**Mutation-guard interaction (R1 seam-seeds) — required for the design to run.** The Phase-0 guard strips a scenario **only when it classifies `mutating && expectsSuccess`** (`classify.ts:40`; `tools.ts:203`). The classifier runs over the **ENTIRE scenario block** (`classifyScenario(block)`, `tools.ts:200`; `classify.ts:33-35`) — including the template-mandatory `**Edge cases:**` section — not just the read assertion. Two failure modes bracket the seam-seed: (1) a **clean-phrased** seed (no negative/blocked token anywhere in its block) IS stripped under the default `allow_mutations: false` — and if it is the only BE scenario, the dispatch set empties and `qa_loop_start` **hard-errors** (`tools.ts:225-229`); (2) a seed whose block carries a **BLOCKED-class token anywhere** — *reject / block / deny / forbidden / unauthorized / must not / should not / no (state change|row|change)* or a `401`/`403`/`4xx` literal (`classify.ts:9-10`), in the read assertion **or any edge case** — classifies `expectsSuccess=false` and is **NOT stripped**: its INSERT **lands even without `allow_mutations`**, on any target; since the template mandates edge cases, a rule-compliant positive read with one routine blocked-class edge case (*"invalid payload → 400"* carries the `4xx` literal) still lands unguarded. (Bare *invalid* / *negative* are NEGATIVE_HINT-only, `classify.ts:11-12` — they set `kind=negative` but do **not** flip `expectsSuccess`, so such a seed is still stripped.) **Authoring rules:** (a) an R1 seam-seed keeps its **entire block** free of negative/blocked phrasing — the read-back assertion AND every edge case positive-phrased; any negative assertion or negative edge case goes in a SEPARATE non-mutating scenario (a single **BLOCKED-class** token anywhere flips `expectsSuccess=false` and lands the INSERT unguarded — `expectsSuccess = !(kind==='negative' && blocked)` with `blocked` alone forcing `kind=negative`, `classify.ts:35,40`; banning ALL negative-ish phrasing is deliberate safe over-coverage); (b) the **dedicated throwaway target (§7) is the only reliable line of defense** for seam-seed writes and is MANDATORY — the guard cannot be relied on to strip every seed; (c) a **read-only** scenario — the R1 seedless branch (b) read, any `(unverified)` covered read, any existence-check/DB-Check-only scenario — keeps its ENTIRE block (assertions, edge cases, `**Coverage delta:**` prose included) free of **write verbs in bare/plural present form** (*create / insert / update / write / save / delete / mutate / persist* — deliberate over-coverage, same stance as rule (a)): `classify.ts:6` `WRITE_STEP` matches them anywhere in the block, a positive-phrased read then classifies `mutating && expectsSuccess` and is **stripped** (`tools.ts:203`) — and a seedless plan carries no `**Seeds fixtures:**` bullet, so the consent gate never fires and **no `allow_mutations` recovery exists**. Phrase existence checks as *"assert a row with `<PK>=<v>` is present"* and deltas as *"the row must be seeded manually"* (past-tense forms and *seed/seeded* do **not** match the regex) — never *"the runner cannot create it"* or *"if the create-path is unavailable"*. **Delivery wiring (stays doc-only):** whenever Step 4.7 authors a `**Seed (psql/sqlite3):**` step, the plan MUST also emit a `## Setup` bullet — `**Seeds fixtures:** BE-NN[, BE-NN…] (requires allow_mutations)` — the **defined Veles→Perun marker** (documented in `test-plan-format` Setup Rules, §5). Perun, on resolving a plan whose `## Setup` carries `**Seeds fixtures:**`, does **not** silently flip the flag — it surfaces a one-line consent gate (*"this plan seeds fixtures via `<enumerated declared DB token(s)>`; confirm the base-url AND every DB the seeds write to — each `$VAR`/DSN declared under `## Setup` `**Required databases:**` and referenced by a `**Seed (psql/sqlite3):**` step — point at a dedicated throwaway instance, never shared/prod"*; the seed's write egress is the **DSN host**, a field separable from the base-url, so the gate must name both) and passes `allow_mutations: true` to `qa_loop_start` only after the user confirms (or the run was invoked with `--allow-mutations`, `run-qa.md:28`). Without that wiring the flagship seed strips or stalls — `perun.md:92` hardcodes `allow_mutations: false` today, so the §10 perun.md row adds this rule. (A cleaner future fix — a `classify.ts` "declared-seed" exemption so seeds run without run-wide `allow_mutations` — is a code change, logged in §8.)

### Move 2 — New Coverage-Matrix disposition `provisioning-blocked`

Today `veles.md:44-47` enumerates exactly three dispositions — `covered` / `blocked-by` / `out-of-scope` — and a **reachable** changed surface marked `out-of-scope` is a hard-stop failure (`veles.md:47`). The BE-03/BE-04 propagation fits **none**: not `covered` (loop can't reach the write path), not `blocked-by` (code is correct — no defect), not `out-of-scope` (a `curl`/`psql` read interface exists). It needs a fourth.

Add **`provisioning-blocked`** to Step 6.7 (complete-the-matrix) and `test-plan-format`'s Coverage-Matrix docs, with this decision boundary:

- `covered` — the loop exercises it.
- `blocked-by` — a **code defect** obstructs an otherwise-reachable path (remediation = revert/fix).
- `out-of-scope` — **no** harness interface can ever observe it (a harness property).
- `provisioning-blocked` — **correct code + a real `curl`/`psql`/`Playwright` interface, but the required precondition artifact is un-creatable by the runner** (a pre-published Temporal+Azure workflow, a third-party-issued artifact).

**Mandatory honesty guard:** a `provisioning-blocked` row MUST carry **either** a `**Setup prerequisite:**` naming the exact human action to provision the artifact **or** a `hermetic: <path>::<test>` pointer (ideally both). A row with neither, or one whose **precondition artifact is actually mintable by the runner's four tools** (then it is `covered`, not `provisioning-blocked` — the litmus below), is a hard-stop defect. Note the disqualifier keys on the *precondition* being mintable, NOT on a read interface existing — every valid `provisioning-blocked` row owns a read interface (that is what separates it from `out-of-scope`). Un-provisionability is strictly a **harness property**, never a code-defect excuse (a genuine defect still routes to `blocked-by`). **The `hermetic:` pointer is itself Step-0-grounded:** the named test file MUST be present in the tree, `::<test>` MUST name a real test in it, and that test MUST assert the *originating producer* the row skips (Move 3). A pointer to an absent/unread file, or to a test that does not exercise the changed logic, is a **hallucinated pointer and a hard-stop defect** — exactly as an ungrounded R1 seam-seed is (`SKILL.md:17`). When no such test exists on disk, the row MUST instead carry a `**Setup prerequisite:**` (the pointer alone is insufficient).

**Tie-break (un-provisionable AND un-observable).** A surface can be both un-provisionable and currently un-observable by all four tools (an un-provisionable UI whose artifact never renders satisfies both `out-of-scope` and `provisioning-blocked`). Decide by **remediability**: if provisioning a single named artifact (a `**Setup prerequisite:**`) would make it observable → `provisioning-blocked`, and the row MUST carry that Setup prerequisite (a hermetic pointer alone is insufficient here — without observability there is no live path to gap-fill); if **no** provisioning action within the four-tool world could ever make it observable (the interface class itself does not exist) → `out-of-scope`.

**Tie-break (defect AND un-provisionable).** When a changed surface both harbors a genuine code defect AND is reachable only after an un-mintable precondition artifact, the **defect takes precedence**: disposition `blocked-by` (a defect is a code fact, not a harness fact), record the BLK entry and state BOTH gates in that entry's `**Remediation (human Setup prerequisite):**` field (template: `test-plan-format:56-60`) — revert/fix the defect AND provision the named artifact — so the reviewer knows the kept contract-correct scenario is doubly-gated before it can run. The BLK entry is the **guaranteed home**: `## Blockers / Findings` is always mandatory (`veles.md:40-41`) and `blocked-by` requires a matching BLK entry, whereas `blocked-by` trips neither arm of the amended matrix gate (a single-behavior diff would have no matrix row to carry a `**Setup prerequisite:**`). `provisioning-blocked` is reserved for correct code — hiding a defect behind provisioning would violate the never-a-code-defect-excuse invariant.

**The litmus + earn-the-punt (the single predicate).** *Un-provisionable* means the precondition/trigger artifact **cannot be produced by the runner's four tools** (`curl`/`psql`/`sqlite3`/Playwright) — it needs a tool or external issuance outside them (a pre-published Temporal+Azure workflow, a third-party-issued token/cert). The question — *can the artifact be minted by a `curl` POST/PUT, a `psql`/`sqlite3` INSERT, or a Playwright action?* — is **often a runtime fact the read-only author cannot settle from the tree**, so `provisioning-blocked` is an **earn-the-punt** claim (exactly like `out-of-scope`'s reachability litmus, `SKILL.md:253-257`): the author MUST first **exhaust the tree for a create-path** (route table / OpenAPI / write-endpoint / factory / migration). If the tree shows a *plausible* create-path, emit the **`covered` live scenario tagged `(unverified — confirm at run time)`** — never punt to `provisioning-blocked`. `provisioning-blocked` is valid only when the tree affirmatively shows the artifact needs an out-of-band issuer the four tools cannot reach. **Undetermined middle (default into coverage):** when the exhausted tree settles mintability NEITHER way — no plausible create-path AND no affirmative out-of-band evidence — author the live scenario that presumes the precondition, tagged `(unverified — confirm at run time)`, with a `**Coverage delta:**` naming the unconfirmed precondition (the same fallback as the R1 seedless branch (b), **including its existence-check first assertion and rule (c)'s write-verb-free phrasing**; the `(unverified)` backstop rules below apply). An un-settleable precondition surfaces as an honest `(unverified)` `covered` gap — never a stall, a silent drop, or a punt. This one predicate gates R0 (Move 1), Move 3's demotion, and the Step 6.8 refute; a row whose precondition IS mintable (or plausibly create-able per the tree) is an invalid `provisioning-blocked` and reclassifies to `covered`. **Backstop for the `(unverified)` escape:** an `(unverified)` `covered` scenario riding an unconfirmed create-path MUST additionally carry (a) a `**Coverage delta:**` naming what goes unproven should the presumed path be unavailable at run time (delta prose obeys rule (c) — no bare write verbs), and (b) a `hermetic: <path>::<test>` pointer as fallback evidence whenever a repo test asserts the same changed logic (known from Step 4.6 test-infra detection) — because be-testing's `(unverified)` handling only **downgrades mismatch severity to LOW**, it performs no reclassification, so without this backstop a wrong plausibility guess degrades to a mis-read LOW mismatch on a row still marked `covered` instead of a pointed, honest gap.

**Necessity for the change (conjunctions).** When a surface needs several preconditions, it is `provisioning-blocked` **only if** at least one precondition **on the causal path of the changed behavior** is un-mintable by the four tools AND no live rung can observe the changed behavior without it. If every precondition needed to observe *the diff's* behavior is mintable — even when some unrelated setup artifact is not — the surface is `covered`. (BE-03/BE-04 is a conjunction: a psql-mintable `user_tasks` row AND an un-mintable pre-published workflow; the workflow is on the causal path of the score's *production*, so the propagation stays `provisioning-blocked` — but a change the mintable subset already reaches is `covered`, not blocked behind the irrelevant un-mintable artifact.)

**Amend the two-way reclassify guard to three-way.** `qa-plan-authoring`'s existing Step-6.8 guard currently reads a **two-way** exit — *if the changed surface has a `curl`/`psql`/Playwright interface or effect, `out-of-scope` is invalid → reclassify to `covered` or `blocked-by`*. Extend it to **three-way**: *"… reclassify to `covered` (reachable now via an artifact the runner can create with its four tools), `blocked-by` (a defect obstructs it), or `provisioning-blocked` (reachable only after a precondition artifact the runner cannot create with those four tools — carries a Setup prerequisite and/or hermetic pointer)."* Without this amendment an honest `provisioning-blocked` row is told to reclassify away.

**Force the matrix (single-surface carve-out).** The Coverage Matrix is otherwise *"required only when the Changes Summary names ≥2 status/behavior classes"* — so a genuinely single-surface un-provisionable change would emit **no** matrix and the `provisioning-blocked` row (with its pointer) would silently vanish, the exact failure this move exists to prevent. **Any `provisioning-blocked` surface forces the matrix even on a single-behavior diff** (a one-row matrix carrying the pointer/prerequisite). Amend the `≥2 classes` gate to *"≥2 classes **OR** any changed surface is `provisioning-blocked`"* at **every** gate that enforces it, or the row vanishes at the un-amended layer: qa-plan-authoring **Step 6.7** (complete-the-matrix — the **binding** author-side gate: amend its opening conditional at `SKILL.md:301` from *"When the surface has ≥2 status/behavior classes, complete the `## Coverage Matrix` drafted in Step 1.5"* to *"…≥2 status/behavior classes **OR** any changed surface is `provisioning-blocked`… (drafting the one-row matrix now if Step 1.5 emitted none)"* — an amendment of that sentence, **not** a new appended one); at **Step 1.5** the `provisioning-blocked` verdict does not yet exist (Step 4.7 assigns it later), so Step 1.5 gains only an ADVISORY note: draft the one-row skeleton if an un-provisionable trigger is already foreseen, else Step 6.7 forces the matrix retroactively — and its *"a one-behavior change needs no matrix"* parenthetical `SKILL.md:94/100` is softened accordingly; `test-plan-format`'s `## Coverage Matrix` header (`:62`) **and its separate inline *"Omit on single-behavior diffs."* clause (`:65`** — rewrite to *"Omit on single-behavior diffs UNLESS a changed surface is `provisioning-blocked`"*) + Plan Quality Checklist (`:368`); and — critically — `veles.md:42-43`, the hard-stop trigger that actually blocks the result JSON (§4a).

**Row-anchoring (Step 6.7).** Step 6.7 excludes an *internal collaborator* (error mapper, use-case, port, lock, adapter) from its own row — *"exercised through a surface, not its own row"* (`SKILL.md:307-308`). A multi-hop propagation whose **terminal effect is a DB-observable write** (`user_tasks.confidence_score`) is anchored as that **DB-observable schema surface** and earns its own `provisioning-blocked` row; the intermediate executor/runner/activity hops are the collaborators exercised through it, not separate rows. So Step 6.7's internal-collaborator exclusion does **not** suppress the flagship propagation row — state this reconciliation in the Step 6.7 edit. **Also neutralize the binary sentence at `SKILL.md:317`** (*"…cannot be `out-of-scope` — only `covered` or `blocked-by`"*) to admit the third disposition: *"…cannot be `out-of-scope`; it is `covered`, `blocked-by`, or (real read interface but a precondition artifact un-mintable by the four tools) `provisioning-blocked`."* — else the Step-6.7 body contradicts the disposition the same edit adds.

### Move 3 — Propagation-vs-read-back honesty (`**Coverage delta:**`)

Add to Step 4.7 (and document the annotation in `test-plan-format`): *"When an R1 seam-seed INSERTs a row and asserts the read-back, it proves the read path, NOT any mutation/derivation the diff introduced **upstream** of the seed. When the changed code IS that upstream producer, the seam-seed is downstream and does not cover the change. **First apply the Move-2 litmus to the *originating* producer — the earliest stage the diff changed, not the terminal write** (for a multi-hop chain like `executor→runner→activity→DB`, the litmus targets the **earliest stage the diff actually changed** — the executor entrypoint *only if* the diff changed the executor; if the diff touched only a mid-chain hop, that hop is the target; a row-write is never the target). If that originating trigger is reachable — a `curl` request, a `psql`/`sqlite3` write, or a Playwright action can drive the real production path *from the top* — **prefer a scenario that fires it and asserts the read-back; that is `covered`**, and the seam-seed is unnecessary. (An INSERT/POST that reproduces the **output of the changed stage** — or of any stage downstream of it — is a seam-seed, not `covered`; it skips the derivation under test. But driving the changed stage **from its own input** — a `curl`/`psql`/Playwright action supplying that stage's real upstream input and reading its output — fires the real changed code and **is `covered`, even mid-chain**. ### Move 4 — Auth-authority grounding (Step 4.6 sub-rule)

Fold into Step 4.6 (Detect the test environment — already `Read`/`Grep`/`Glob` only, no new Bash token): *"When a scenario needs an authenticated call, GROUND the token issuer/authority against the app's real auth config — never guess a well-known endpoint. Read the auth settings in the tree (issuer/authority/tenant/token-url, the `.well-known/openid-configuration` reference, the auth dependency's configured base) and derive the binding recipe login URL + `Egress:` host FROM that. A hard-coded `login.microsoftonline.com` when the app's configured authority is a CIAM tenant (`<tenant>.ciamlogin.com`) is a grounding defect."*

**Bound (VALUE vs NAME).** Grounding extracts only the **non-secret routing value** (issuer/authority hostname, tenant slug, token-URL) — it MUST NOT copy any secret VALUE into a recipe/binding/env. Step 4.6 already reads config *including* `.env`/`.env.test`/`.env.local` but emits env-var **names only, never values**; auth-grounding stays under that rule. **Classifier (which `.env` line is inlineable):** treat an authority as inlineable **only when it is a bare routing endpoint** (hostname / URL / tenant slug with no secret component) — the SAME class Step 4.6 already inlines for base-url and DSN hosts (`SKILL.md:190`) while keeping secret vars names-only (`:197`). If the entry is a token, key, password, credential-bearing connection string, or any value whose disclosure grants access, it is a SECRET: emit its NAME only, never inline, and use the runtime-only carve-out below. When in doubt, treat it as a secret and declare `$AUTHORITY`/`$ISSUER` as a Required env var. A credential-prefixed authority name (e.g. `AZURE_AUTHORITY`) still follows the denylist; **declaring** it in the plan is what makes it pasteable (Move 5), never a neutral alias.

**Runtime-only carve-out (decision locked — prefer the var):** when the authority is injected at deploy time and not readable in the tree, **declare `AUTHORITY`/`ISSUER` as a Required env var, ALSO list it in the binding's `Inputs:`** (e.g. `Inputs: $AUTHORITY, $TEST_USER_EMAIL`), and reference `$AUTHORITY` in the recipe (grounded-by-paste — one predictable pattern). A recipe `$VAR` absent from that binding's `Inputs:` is rejected by `parse_plan` (`binding-parser.ts:177-181`; `test-plan-format:171`); Required env vars are presence-probed only and are **not** auto-substituted into recipes. **Whole-authority constraint:** when `$AUTHORITY`/`$ISSUER` is the binding `Egress:` and appears in the recipe URL, the var MUST be the **entire authority** (`Egress: $AUTHORITY`; recipe `"$AUTHORITY/<tenant>/oauth2/v2.0/token"`) and the pasted value MUST be a bare `scheme://host` with **no path** — the token URL's path/tenant lives in the recipe string *after* `$AUTHORITY`, never inside the pasted value. `hostOfURL` (`recipe-validator.ts:229`, whole-authority rejection at `:236-247`) enforces this on the **template** — it rejects a binding whose recipe/`Egress:` token carries an in-token suffix (`$AUTHORITYevil`, `$AUTHORITY/path`), so the author cannot write a mismatched egress. But the pasted VALUE is **not** re-validated against egress at run time (`validateRecipe` runs only at parse time, `binding-parser.ts:185`; `execute-recipe.ts:97` shell-expands the composed value with no egress re-check). So the bare-`scheme://host`-no-path requirement on the pasted value is an **operator/paste-time contract, not a machine check** — state it as an explicit paste-time instruction in the binding/preflight prose, never as a guaranteed rejection. The `(unverified — confirm at run time)` tag remains a permitted last resort, but the declared-var form is the authored default. Cross-reference OMO `app-server.md:8-9,21-25`.

**Multi-principal.** The grounded authority — the derived login URL + `Egress:` host, or the declared `$AUTHORITY`/`$ISSUER` var — is an **app-level** property shared across all principals. When Step 6.5 mints a second-principal binding (IDOR/RLS tests) it substitutes only the per-user **credential** inputs and reuses the **same** grounded authority/`Egress:` (references the same `$AUTHORITY`/`$ISSUER` var) — never a re-guessed endpoint for user B. It must independently declare `$AUTHORITY`/`$ISSUER` in **its own** `Inputs:` (Inputs are per-binding — there is no ambient recipe env), reusing the same value/`Egress:` and substituting only the per-user credential inputs. A second-principal binding whose authority is un-grounded is the same grounding defect as the first.

## 7. Runner-scope compliance & coverage tradeoff

**Scope:** every authored artifact stays within `curl`/`psql`/`sqlite3`/`Playwright` against an already-running instance. Nothing requires `docker`/`make`/build/mock-standup. **Seam-seed writes** (R1) require the run to be invoked with `allow_mutations` — safe precisely because QA targets the mandated **dedicated throwaway instance AND throwaway DB, both named by the seed consent gate** (the seed's write egress is the declared DSN host, separable from the base-url; never shared/prod); this is an existing run-invocation flag, not a qa-loop code change (Move 1 mutation-guard interaction).

**Consciously accepted tradeoff:** we give up **live** end-to-end coverage of the `confidence.score` propagation (the runner cannot create the upstream Temporal+Azure workflow). We keep the **read-back** path via an R1 seam-seed (the BE-01/BE-02 pattern), and keep it **honest** with three interlocking controls: (1) the `**Coverage delta:**` line names what the seed does not prove; (2) the propagation gets its own `provisioning-blocked` row with a mandatory `hermetic:` pointer to the test that *does* exercise it; (3) Step 6.8's refute pass makes an unlabeled downstream seed a hard failure, and the Veles hard-stop rejects a `provisioning-blocked` row lacking a pointer/prerequisite. Net: a loop that cannot exercise the changed path now **says so and points at what does**, instead of faking a green or silently dropping the surface — OMO's "missing evidence = QA did not happen" applied to the un-provisionable case.

**Residual human engagement:** stand up / point QA at a dedicated non-prod instance + throwaway DB, and paste the **minimized** secret set once (now without the false "must export + restart" wall). Publishing the real workflow for live propagation coverage becomes **optional** (green-with-honest-gap without it) rather than a hard stall.
